1

The controller stays thin

Spring Security hands it the signed-in maker, and @Valid rejects bad input before any business logic runs. Everything else is delegated.

2

Ownership on every lookup

Products and channels are fetched by id and maker. Someone else's product simply doesn't exist for you: a 404, never a data leak.

3

One guarded statement decides

The database lowers stock only if enough remains. Zero rows updated means the sale is refused with a 409. No read-then-write race.

4

Ledger in the same transaction

The sale copies the unit cost at that moment, then saves. @Transactional makes stock and ledger commit together, or not at all.

Follow one request. Step 1: the controller is thin. It gets the authenticated maker from the JWT and validates the body. Step 2: every lookup includes the maker id, so you can only touch your own data. Step 3: a single guarded UPDATE decides whether stock is available, which removes race conditions. Step 4: the sale is saved in the same transaction, with a snapshot of the unit cost so past profit never changes.

1

No server sessions

Nothing is remembered on the server between requests. Each request carries its own proof of identity, so the API scales and restarts cleanly.

2

A filter checks every call

It reads the Bearer token, verifies the signature and expiry, and puts the signed-in maker into the security context.

3

Locked by default

Only sign-up and login are open. Every other /api route requires a valid token; everything else is just the React app.

4

Signed, expiring tokens

Tokens carry the maker id and an expiry, signed with a secret from the environment. Passwords are stored only as BCrypt hashes.

Security is stateless. A filter validates the JWT on each request. Only register and login are public; every other API route needs a token. Tokens are signed with a secret that comes from an environment variable, and passwords are stored as BCrypt hashes.
Code walkthrough · database

A schema that protects itself

V1__init.sql · Flyway migration (excerpt)
CREATE TABLE sales ( id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, maker_id BIGINT NOT NULL REFERENCES makers(id) ON DELETE CASCADE, product_id BIGINT NOT NULL REFERENCES products(id), channel_id BIGINT NOT NULL REFERENCES channels(id), quantity INTEGER NOT NULL CHECK (quantity > 0), unit_price NUMERIC(12,2) NOT NULL CHECK (unit_price >= 0), unit_cost NUMERIC(12,2) NOT NULL CHECK (unit_cost >= 0), sold_at TIMESTAMP WITH TIME ZONE NOT NULL ...); CREATE INDEX idx_sales_maker_date ON sales(maker_id, sold_at); -- products tablestock INTEGER NOT NULL CHECK (stock >= 0),CONSTRAINT uq_products_maker_sku UNIQUE (maker_id, sku)
1

Normalized and linked

Each sale points to its maker, product and channel with foreign keys. No duplicated names, no orphan rows.

2

Rules live in the database

No negative stock or prices, quantity above zero, one SKU per maker. Even a bug in the app can't write bad data.

3

Cost is snapshotted

Each sale stores the cost at the time. Edit a product's cost later and last month's profit stays correct.

4

Indexed for the questions we ask

Maker plus date range is exactly how the dashboard and ledger filter. Flyway applies this same schema in every environment.

The database enforces the rules. Foreign keys keep data normalized, CHECK constraints prevent invalid values, and a unique constraint keeps SKUs unique per shop. The sales table snapshots unit cost so history never changes. An index on maker and date matches the dashboard and ledger queries, and Flyway applies the identical schema everywhere.

Reflection

What changed, and what I learned

ProposalWhat I shippedWhy
Azure App Service + Static Web AppsOne Docker image, Render blueprintAnyone can run or view it without cloud credentials
Caching layer for readsAggregates computed in PostgreSQLFast enough at this scale; less to maintain
Azure Blob image storageLocal disk behind a storage classSimple now; one class to swap later

Lesson: push consistency into the database, ship the simplest architecture that works, and keep the docs honest about what's real.

Three deliberate deviations. I simplified hosting to a single container so a reviewer can run it with one command, I skipped a separate cache because the aggregate queries are fast, and images stay on local disk behind one class that's ready for object storage. The biggest lesson: let the database enforce consistency, and describe the system as it actually is.
